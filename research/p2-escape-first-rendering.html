面向 LLM 输出的转义优先渲染管道

An Escape-First Rendering Pipeline for LLM-Generated Markdown
2026-10 LY AI HUB 巨天agent v7.0.0 3 渲染面审计
摘要 — 智能体界面渲染的每一行 Markdown 都来自模型输出,而模型输出是不可信输入:一条被注入 <img onerror> 的回复一旦进入 innerHTML,就在一个能调用终端工具的同源渲染进程里获得执行权。我们对巨天agent 的全部 Markdown 渲染面做了系统审计,共识别 3 个面:桌面代码模式预览(存在可执行注入,已修复)、手机远程单页(转义正确,但脚本协议链接未拦,已中和)、知识库打印管线(先转义,安全)。本文给出修复所采用的「先转义、再增强、后中和」三段式管道,并给出攻击载荷与修复后的行为对照。

01威胁模型:同源注入即工具执行

巨天agent 的渲染进程与后端 :3211 同源,具备调用 /api/tools/execute(含 shell)的能力——这正是产品形态的要求。因此传统的「XSS 只能偷 Cookie」评估在这里不成立:本场景下一次成功的注入近似于本机任意命令执行。注入源有三:模型输出(可被提示词诱导)、被预览的仓库文件内容、工具返回的网页抓取结果。三者都不可信。

03修复:三段式管道

修复后的 renderMarkdown(src/renderer/code/MarkdownPreview.tsx)遵循三段式:

  1. 先转义——管道第一步统一处理 & < > "。引号必须转义:否则 [x](a" onmouseover="…) 可从 href 属性破出。
  2. 再增强——既有 Markdown 正则(标题、粗体、列表、代码块)在已转义文本上运行,生成的标签全部由管道自己产出。代码块内容因此无需二次转义(避免双重转义显示错误)。
  3. 后中和——渲染完成后统一 neutralize href/src="javascript:|vbscript:…",覆盖 markdown 链接语法引入的脚本协议。
// 修复后管道首尾(节选)
const html = md
  .replace(/&/g,'&').replace(//g,'>').replace(/"/g,'"')
  .replace(/```(\w*)\n([\s\S]*?)```/g, (_,l,c) =>
    `<pre...><code...>${c.trim()}</code></pre>`)   // 内容已转义,不再二次
  ...
  .replace(/ (?:href|src)="(?:javascript|vbscript):[^"]*"/gi, ' href="#"')

手机远程单页同日加固:其管道本就以 text.replace(/</g,'&lt;') 先转义再进 marked,脚本注入不可行;本次补上同样的 scheme 中和。

04局限

  • 正则级 Markdown 渲染不做完整规范解析,遇到极隐蔽的构造(如嵌套属性拆分)建议以「先转义」为唯一防线——本管道正满足该性质:所有原始元字符在增强前已被消灭。
  • data:image/… 图片地址未拦(预览场景无害);若未来预览用于不可信协作场景,需引入 allowlist。
  • 主对话气泡的渲染由 React 自定义组件完成(默认转义),不在本文审计范围;后续可对齐同一三段式以统一实现。
